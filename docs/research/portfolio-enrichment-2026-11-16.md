# Portfolio enrichment research — 2026-11-16

## Scope and evidence

This note covers the ten scenarios in [the portfolio guide](../ten-game-portfolio.md) and its two additional card games. It is a backlog proposal, not a claim that these features have shipped or that the games have been balanced with players. The scenarios mostly provide content to six existing family authorities; changing one family can affect other presets. The card games have separate authorities and a shared pile provider. Findings below come from the portfolio guides and content, `src/sdk/contracts/`, family and card consumers, reuse discovery and the Assetrizz provenance. The existing documented headless winning routes and browser one-action checks are useful baselines, not evidence of subjective replay value, accessibility or complete browser playthroughs.

**Priority:** P0 = improve understanding and reliable operation first; P1 = modest, measurable replay value; P2 = higher-cost experiments after playtesting. Estimates are relative, not commitments. Prefer optional, clearly described challenges that preserve a normal completion route. Do not assume that more randomness, metaprogression or compulsory scores makes a game deeper.

## Reuse decision record and boundaries

Discovery used short queries for outcome ratings, piles, input/pause, storage, ordered rounds, objectives and graph paths, plus `--show` on the relevant recipes. See [REUSE.md](../../REUSE.md) and [REUSE_INDEX.md](../../REUSE_INDEX.md) for dependencies, selected roles and linked tests.

| Need | Candidate IDs | Decision and boundary |
|---|---|---|
| Results / optional mastery | `mechanics/outcome-rating`, `recipe/outcome-ratings` | Reuse existing race/tactics classification; thresholds and metrics are game policy. Current race thresholds are fractions of the time limit and tactics gold uses turns and survivors; tune only from playtest data. Provider does not collect metrics, establish victory or save records. |
| Local bests and preferences | `recipe/profile-storage`, `sdk/Profile` | Reuse optional host service for small namespaced values. Profile values are strings, numbers or booleans, and `save` replaces the whole profile without atomic read-modify-write: merge validated existing values, handle unavailable/corrupt/incompatible results, and avoid clobbering other games. Version record keys by preset, rules/content version and assist mode; establish comparison direction and tie behavior. This is not a run-save API. |
| Gates and tactical queries | `mechanics/sequence`, `recipe/ordered-rounds`, `mechanics/navigation`, `recipe/ordered-navigation` | Reuse existing family integrations. Sequence does not detect crossings or time laps; navigation is ordered unit-edge search, not weighted movement or a collision system. Authority rechecks occupancy, AP and legality. |
| Resources / objectives | `mechanics/kits`, `mechanics/resources`, `mechanics/actions`, `mechanics/clock`, `mechanics/objectives`, `recipe/resource-actions`, `recipe/objective-unlocks` | Reuse explicit clocks, costs and receipt-deduplicated counters; retain the family-specific validity, consequences and objective restrictions. Counters do not themselves award progress across runs. |
| Cards / input | `portfolio-cards/piles`, `recipe/ordered-card-piles`, `recipe/scoped-input`, `recipe/bounded-command-queue` | Reuse owned partitions and semantic ingress. Preserve pause gating and disposal; games validate commands and own card effects. No existing shuffle or arbitrary card-zone API is claimed. |
| Story and puzzles | `story/adventure`, `puzzle/rules`, `sdk/Adventure`, `sdk/PushPuzzle` | Extend the owning family only for missing branch result, selection or observation behavior. Chapter action replay saves are not interchangeable with generic serialized state; puzzle navigation is not a push-puzzle solver. |

Avoid a new generalized progression or challenge provider until at least two consumers demonstrate the same concrete semantics; records, challenge eligibility and optional objectives may have materially different policies.

## Accessibility and control design

* Provide keyboard access to menus, choices and equivalent gameplay actions; native buttons, visible focus, logical tab order and a persistent control reminder are the baseline. Respect editable controls and input contexts; do not route Space/Enter simultaneously to a focused button and gameplay. Consider configurable bindings, toggle alternatives for sustained drift, larger touch targets and adjustable game speed as follow-up work, not presumed existing features. Real-time assists should be optional, clearly labeled, and records kept separate when rules or speed change.
* Pair color with readable names, shapes or patterns for Crosswind destinations, tactical teams/cover and race gate state. State changes and essential audio cues need text or visible equivalents; avoid relying on animation or sound alone. Prefer non-intrusive announcements for committed outcomes rather than repeatedly announcing every frame. Check text contrast, zoom, focus visibility, reduced motion and controls on narrow screens.
* For navigation and spatial play, test the full experience with keyboard and assistive technology: DOM controls alone do not make a 3D board or real-time flight screen-reader accessible. Add a meaningful textual state/selection alternative where needed, and explicitly test whether it conveys spatial relationships. Keep tutorials and hints optional, repeatable and player-paced; avoid making the first encounter or first result dependent on memorizing an external guide.
* Grounding: W3C's [Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) explains why a visible non-color cue matters; [Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) discusses keyboard equivalents and timing. The [Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/full-list/) recommend remapping, game-speed choices, control/objective reminders and feedback from disabled players. These sources inform design; they do not establish conformance of this build. Include disabled participants and different input methods in actual usability sessions.

## Assetrizz: grounded presentation opportunities

The shipped selection and exact source revision, hashes, dimensions and orientation are recorded in [`assets/experiences/provenance.json`](../../assets/experiences/provenance.json) and its [README](../../assets/experiences/README.md). `theme/arcade` includes a track tile, cropped pennant, wide backdrop and a **side-view decorative scooter badge**; the playable top-down car is procedural. `theme/board` includes a voxel explorer, chalk golem, rock cover and boardwalk tile. `theme/story` includes an exterior observatory plate, keeper portrait, loupe and brass key; the current two chapters reuse observatory imagery. These are single frames, not animation strips; audio is synthesized rather than Assetrizz samples.

Use existing semantic theme keys and a consistent symbol/label overlay for status and challenge cards. Board cover art can support tactical explanations and the golem can illustrate pursuit without implying a new enemy. The story key/loupe and keeper portrait can frame a journal, but an observatory exterior should not be presented as a bespoke seedship interior. A stronger visual identity for each chapter needs verified appropriate source artwork and an explicit theme/presentation mapping, not a misleading relabel. If importing other Assetrizz imagery, verify source suitability, crop/orientation, pin revision and hashes and follow the existing import/provenance workflow. The provenance says “original, generated for Kyle Durepos”; it does **not** assert an MIT or broader license grant.

## Verification and rollout

1. Baseline before implementation: run the documented `tests/portfolio-{puzzles,racing,tactics,adventures,resource-games}.test.ts`, `tests/portfolio-cards.test.ts`, and `tests/outcome-rating.test.ts`; use `tests/portfolio-demo/run.mjs` for browser integration. Inspect current screens and capture actual issues before describing a feature as missing.
2. For each new authored variation, run complete positive and negative authoritative traces, terminal ordering, invalid-command no-mutation and retry; exercise pause/resume and lifecycle disposal. For cards, check unique-ID conservation and determinism for each authored order. For races, cover multiple ordered crossings per frame, reverse crossings, timeout, split ordering and repeat runs. For tactical previews, compare against the authority and test stale-state revalidation. For story, test each choice, chapter-isolated save/load and invalid/versioned saves.
3. For records, cover absent/unavailable/corrupt storage, invalid/nonfinite values, worse and tied results, key/version/assist isolation and preservation of unrelated profile keys. Explicitly define failure feedback and behavior on storage failure; gameplay must remain playable.
4. Run `npm run index-reuse` if source/catalog/metadata changes, `npm run check`, bundled validation, and build/smoke for browser-facing changes as required by [AGENTS.md](../../AGENTS.md). Add focused browser journeys for keyboard, focus, touch where supported, labels and results—not merely screenshot snapshots. Manually verify audio/pointer-lock changes in a real browser. Run human playtests for legibility, difficulty and replay motivation; record participant tasks and observations separately from automated pass counts.

**Suggested first slice:** Crosswind destination labels and Last Rain action/forecast explanations, plus tactical previews where not already shown. They use existing authoritative observations and directly test whether players understand their decisions. Next, add per-track bests with bounded profile persistence, then select one authored variant in each family and measure whether players voluntarily replay it.
